## 4. Новая архитектура SMC Visualizer Pro

### 4.1 Архитектурные принципы (tenets)

| # | Принцип | Формулировка | Как проверяется |
|---|---|---|---|
| T-1 | **Visual never decides** | Visual Engine не принимает торговых решений и не меняет логическое состояние. Он только визуализирует состояние ядра | Код визуального слоя не пишет в реестр и шину. Code review по чек-листу |
| T-2 | **Single source of truth** | Один код детектора для chart TF и HTF. Одно событие — один источник для визуала, алертов и дашборда | Нет дублирующих детекторов. Одинаковые события на графике и в алерте |
| T-3 | **Bar-close determinism** | Логическое состояние меняется только на подтверждённом баре. Одинаковые данные → одинаковые события | Repaint-аудит: журнал событий realtime == журнал пересчёта истории |
| T-4 | **Compute ≠ Display** | Выключение отображения не выключает вычисление, нужное потребителю ниже по графу | Матрица зависимостей (§4.6) |
| T-5 | **Budgeted rendering** | Любой объект на графике получен через бюджет и приоритет | Лимиты 500/500/500 не достигаются (Debug-счётчики) |
| T-6 | **Explainability** | Каждый сетап и событие несут происхождение (`causeId`) — цепочку причин | Analysis Mode воспроизводит цепочку для любого сетапа |
| T-7 | **Price Action First** | Свечи — главный элемент. Визуал помогает читать цену, а не конкурирует с ней | VAC-1, VAC-14, VAC-20 |
| T-8 | **Automation-ready contracts** | Signal / TradePlan / Risk / Webhook определены в v1.0, даже если исполнение появится в v2.0 | Схемы в §9–12 стабильны и версионированы |
| T-9 | **Layer independence** | Логика, визуализация, сигналы, сетапы, риск и исполнение — независимые слои с односторонними зависимостями (вниз по потоку) | Граф зависимостей ацикличен (§22) |
| T-10 | **Graceful degradation** | Нет объёма, мало HTF-истории, нестандартный график → функция деградирует с явным предупреждением, а не молча | Ribbon/Debug показывает статус |

### 4.3 Логический конвейер и шина событий

Основной поток (из постановки, уточнён):

```
                         MARKET DATA (chart TF)        CONFIRMED HTF BARS
                                │                              │
                                ▼                              ▼
                           DATA ENGINE  ◄──────────────────  HTF FEED
                                │          (те же движки, TF slot = HTF)
                 ┌──────────────┴──────────────┐
                 ▼                             ▼
          STRUCTURE ENGINE              LIQUIDITY ENGINE
          ┌──────┼──────┐               ┌──────┼───────┐
          ▼      ▼      ▼               ▼      ▼       ▼
        SWING   BOS   CHoCH/MSS       LEVELS  EQ/KEY  SWEEP/TAKEN
          └──────┼──────┘               └──────┼───────┘
                 └──────────────┬──────────────┘
                                ▼
                           ZONE ENGINE ──────► OB · BB · MB · RB · FVG · IFVG · (VI · LV · BPR · SD)
                                ▼
                          CONTEXT ENGINE ────► Dealing Range · PD · OTE · Session/KZ · HTF Bias · Regime
                                ▼
                           SETUP ENGINE  (модели: Sweep Reversal, Continuation, …)
                                ▼
                         CONFLUENCE SCORE  (0–10, грейд, разбор факторов)
                                ▼
                           SIGNAL ENGINE   (фильтры, кулдаун, дедупликация)
                                ▼
                            RISK ENGINE    (SL/TP/RR · v2: sizing)
                                ▼
                            TRADE PLAN
                                ▼
                         EXECUTION LAYER   (v1.0: интерфейс · v2.0: strategy/webhook)
                                ▼
                          AUTOMATION v2+   (внешний Execution Gateway)
```

> **Почему Zone Engine стоит до Context Engine** (в постановке Context шёл раньше): OB рождается из события пробоя (Structure), а Context использует уже созданные зоны (например, OTE ∩ FVG). OTE как *уровень* вычисляется в Context, как *зона входа* — в Setup Engine. Атрибут «location» (premium/discount) зона получает от Context **на следующем шаге того же бара**: Context не меняет логику детекции зон, только аннотирует их.

Параллельная шина:

```
          ALL LOGICAL ENGINES (L1–L4)
                     │  emit(Event)  — только на подтверждённом баре
                     ▼
     ┌───────────────────────────────────┐
     │             EVENT BUS             │  barEvents[] (очередь текущего бара)
     │                                   │  history ring (≤ 300 событий)
     │                                   │  lastByType{} (быстрый доступ)
     └───────────────────────────────────┘
          │              │              │              │
          ▼              ▼              ▼              ▼
    VISUAL ENGINE   ALERT ENGINE    ANALYTICS       DASHBOARD/RIBBON
          │              │              │              │
          ▼              ▼              ▼              ▼
     TradingView    alertcondition   Outcome         Table UI
     drawings       alert() → JSON   Tracker,
                    → Webhook        log.* (Debug)
```

**Ключевое требование:** Visual Engine **никогда** не определяет торговую логику. Relevance Score (§16) — чисто визуальная величина и **никогда** не попадает в Setup/Confluence. Confluence Score — логическая величина, визуал лишь отображает её.

### 4.5 Порядок исполнения на баре и каденс обновлений

**Порядок (фиксированный, детерминированный):**

1. `Config Resolver` — один раз (`var`), затем только чтение.
2. `Data Engine` — `BarCtx` текущего бара.
3. `HTF Feed` — если закрылся HTF-бар, прогон HTF-инстансов Structure → Liquidity → Zone на этом баре (TF slot = HTF), эмиссия HTF-событий.
4. `Structure Engine` (chart TF): internal, затем swing.
5. `Liquidity Engine`: новые уровни из свингов, затем проверка свипов и пробоев текущим баром, затем Key Levels.
6. `Zone Engine`: новые зоны по событиям пробоя и FVG-паттернам, затем обновление lifecycle всех активных зон текущим баром.
7. `Context Engine`: dealing range → PD/OTE → сессии → HTF bias → режим → `MarketContext`.
8. `Setup Engine` → `Confluence` → `Signal` → `Risk` → `TradePlan`.
9. Шина: `barEvents` → `history`.
10. Sinks: Alert Engine (батч) → Analytics/Logger → Visual Engine → Dashboard/Ribbon.

**Правило видимости внутри бара:** движок видит события движков, стоящих **раньше** него в порядке. События более поздних движков видны на **следующем** баре (one-bar latency rule). Обратных зависимостей в пределах бара нет.

**Каденс обновлений:**

| Что | Когда исполняется | Комментарий |
|---|---|---|
| Logical update (шаги 2–9) | Только на подтверждённом баре (`barstate.isconfirmed`). На истории это каждый бар | На realtime-тиках ядро не меняет состояние |
| Visual full render | Один раз на `barstate.islastconfirmedhistory` | Отрисовка всей видимой истории из реестра. Результат фиксируется (commit) |
| Visual incremental | На каждом подтверждённом realtime-баре | Только «грязные» объекты (изменились состояние, ранг или геометрия) + пересчёт приоритетов |
| Live layer | На каждом realtime-тике | Только «живые» элементы: положение цены в Ribbon, прогресс активного сетапа, превью (пунктир) формирующихся событий. Дешёвые `set_*` поверх зафиксированного состояния |
| Dashboard/Ribbon | `barstate.islast` | Таблицы создаются один раз, затем обновляются ячейки |

> На исторических барах визуальный слой **не исполняется**. Это главный выигрыш производительности: логика проходит всю историю, а отрисовка — один раз.

### 4.6 Граф вычислительных зависимостей (demand-driven)

|---|---|

### 4.7 MTF-архитектура (HTF Feed)

**Цель:** HTF-анализ без repaint, тем же кодом, что и chart TF.

**Схема:**

```
request.security(tickerid, HTF, [o,h,l,c,v,t,atr][1], lookahead_on)   ← подтверждённый HTF-бар
            │
            ▼  смена HTF-бара (изменилось t)
   HTF Bar Buffer (кольцо, ≤ 500 HTF-баров)
            │
            ▼
   Structure(HTF) → Liquidity(HTF) → Zone(HTF)     ← те же функции, TF slot = HTF
            │
            ▼
   HTF-объекты в общем Registry (tf = HTF) + HTF-события в шине
```

**Правила:**

1. Только подтверждённые HTF-бары. Идиома «значение со смещением `[1]` + `lookahead_on`» отдаёт закрытый HTF-бар с первого LTF-бара следующего HTF-периода одинаково на истории и в realtime. Формирующийся HTF-бар в логике **не используется**.
2. **Один** вызов `request.security` на HTF возвращает кортеж OHLCV + time + ATR. Детекторы работают на LTF-стороне по буферу HTF-баров. Код детекторов общий.
3. **Бюджет запросов v1.0:** HTF1 feed (1), HTF2 bias feed (1, опционально), Daily key levels (1), Weekly key levels (1). Итого ≤ 4 из лимита платформы (40 уникальных вызовов). Резерв на v2: SMT (второй символ), lower-TF данные для CVD.
4. **Глубина истории:** HTF-буфер наполняется из истории графика. Если HTF-баров < `minHtfBars` (по умолчанию 100), то: (а) Ribbon/Dashboard показывают ⚠ «HTF history low»; (б) HTF bias помечается как ненадёжный и не даёт баллов в скоринге; (в) предлагается авто-HTF.
   *Fallback (спайк S-2):* вычисление ключевых HTF-пивотов внутри контекста `request.security` — там доступна собственная история HTF. Используется только для HTF-уровней, без полноценного lifecycle.
5. **Авто-HTF** (по умолчанию):

| Chart TF | HTF1 (структура/зоны) | HTF2 (bias, опц.) |
|---|---|---|
| ≤ 1m | 15m | 1H |
| 2–5m | 1H | 4H |
| 10–15m | 4H | D |
| 30m–1H | 4H | D |
| 2H–4H | D | W |
| D | W | M |
| W | M | — |
| M | — (HTF выключен, ⚠) | — |

6. HTF ≤ chart TF → HTF выключается с предупреждением (AC-26).

**Реализация v0.3 (отклонение от ADR-03, осознанное).** Детекторы движков графика опираются на динамические смещения истории (`low[k]` с переменным `k`), а буфер истории в контексте `request.security` нельзя задать явно. Поэтому **детекция** HTF (пивоты, BOS/CHoCH, OB-кандидат ноги, FVG) записана компактно, только с фиксированными окнами, в функции `f_htfState` (`src/11_htf_feed.pine`), которая исполняется внутри `request.security` на HTF-серии. Это даёт полную HTF-историю (bias корректен даже на M1 при недельном HTF — риск P-06 снят). Каждое значение возвращается со смещением `[1]` при `lookahead_on`, то есть график видит только закрытый HTF-бар — одинаково на истории и в realtime. **Жизненный цикл** не дублируется: HTF-объекты (уровни, OB, FVG) попадают в общие реестры с `tf = HTF1` и проходят те же автоматы на барах графика (свипы HTF-уровней, касания и конверсия HTF-зон). Один `request.security` на HTF (бюджет запросов: 3 из 40). После ревью v0.3: OB-кандидат строится по окну A.7 из кольца последних `len + 4` HTF-свечей (пересборка ноги при подтверждении пивота); пробои и OB передаются отдельно по направлениям; кортеж дополнен временем открытия и номером текущего HTF-бара (известны при открытии, смещение не нужно) — бар графика, который начался раньше открытия HTF-бара (пары W→M, 45m→4H), сохраняет прежнее состояние, и realtime совпадает с историей (AC-25); bias признаётся надёжным при ≥ `Min HTF bars` подтверждённых HTF-барах (A.16). Возраст HTF-объектов на графике считается в HTF-барах (номер подтверждённого HTF-бара при приёме и сейчас), предел дистанции — ×max(3, √соотношения ТФ).

### 4.8 Политика подтверждения и repaint (Repaint & Confirmation Policy)

| Класс | Примеры | Когда появляется | Может ли исчезнуть/измениться | Алерты / webhook |
|---|---|---|---|---|
| **Confirmed** | BOS, CHoCH, Sweep, Zone created/touched/mitigated/broken, Setup stages | На закрытии бара события | Нет (неизменяемо) | Да |
| **Delayed-confirmed** | Swing pivot (HH/HL…), EQ | Через L баров после пивота. Метка ставится **в прошлом** на бар пивота | Нет. Задержка документирована, это не repaint | Да (время события = бар подтверждения) |
| **HTF-confirmed** | HTF BOS, HTF OB/FVG, HTF bias | На первом LTF-баре после закрытия HTF-бара | Нет | Да |
| **Developing** | Weak high диапазона, текущий session high/low, PDH/PDL текущего дня | Обновляются на каждом подтверждённом баре | Да, по определению (стиль «developing» — пунктир) | Только события-переходы (например, «range established») |
| **Preview** (только визуал) | «Возможный BOS» на текущем незакрытом баре, прогресс к уровню | На realtime-тике | Да, исчезает при откате тика | **Нет**, никогда |

Обязательная пометка в документации пользователя: «Свинги подтверждаются через N баров. Метки HH/HL ставятся на бар пивота. Это задержка, а не перерисовка».

**Warm-up:** первые `max(300, 20 × swingLen)` баров истории — прогрев. Сетапы, сигналы и алерты не генерируются, Ribbon показывает «WARMING UP». Причина: состояние автоматов в начале истории зависит от точки начала загрузки и сходится через несколько свингов.

### 4.9 Архитектура отрисовки

1. **Пулы объектов по слоям.** На старте создаются пулы box/line/label в порядке z-слоёв (снизу вверх): `wash` (PD, сессии) → `zones HTF` → `zones LTF` → `levels` → `structure lines` → `setup composition` → `labels`. Порядок создания задаёт порядок наложения (подтвердить спайком S-5). Объекты переиспользуются через `set_*`. `delete` — только при сокращении бюджета.
2. **ViewHandle** (визуальный двойник) хранится в Visual Engine: `id логического объекта → {box, line, mid, label, renderHash, tier}`. Логические объекты не содержат drawing-полей (они должны быть сериализуемы и пригодны для strategy и `request.security`).
3. **Dirty-check:** `renderHash` = f(state, геометрия, tier, opacity-bucket, labelText). Совпадает → `set_*` не вызывается.
4. **Координаты:** исторические объекты — `xloc.bar_time` (устойчиво к сдвигу окна истории и к ограничениям расстояния по bar_index). Проекции вправо (setup-композиция, теги уровней, правый край зон) — время «последний бар + k × длительность бара» или `bar_index + k` при k ≤ 500 (ограничение платформы на будущее).
5. **Правый край зон** — единая вертикаль «now + 5 баров» для всех активных зон. Выровненные края создают спокойный ритм и не уходят в бесконечность (`extend.right` не используется).
6. **Отрисовка за свечами:** `behind_chart = true` в объявлении индикатора (параметр v6; подтвердить спайком S-5) — зоны не перекрывают свечи.
7. **Текст зон** — через `box.text` (тег внутри бокса), без отдельного label. Это экономит бюджет меток.

### 4.11 Организация кода и сборка

Pine не поддерживает `include`. Публикуемый invite-only скрипт с ядром в публичной библиотеке раскрыл бы IP (P-12). Решение — **модульные исходники + сборка в монолит** (ADR-04).

**С v0.4.1 — два монолита из одних исходников (ADR-13).** v0.4.0 (≈40 тыс. токенов) перестала укладываться в лимит компилятора TradingView («Pine compilation was timed out», ~2 мин), тогда как v0.3.0 (≈30 тыс.) компилируется около минуты: время компиляции растёт быстрее размера. Поэтому сборка выпускает два индикатора, каждый — в бюджете ≤ 34 тыс. токенов (с v0.8.1 бюджет считается в токенах кода, где строковый литерал — один токен: ≤ 30 тыс.; v0.3.0 — 26,7 тыс., v0.4.0 — 35,1 тыс.):

| Индикатор | Файл | Что внутри |
|---|---|---|
| **SMC Visualizer Pro** (цель `core`) | `dist/SMC_Visualizer_Pro.pine` | Движки + рендер истории (зоны, уровни, структура, диапазон, сессии), Ribbon, Dashboard, Debug, алерты структуры / ликвидности / зон |
| **SMC Pro · Setups** (цель `setups`) | `dist/SMC_Pro_Setups.pine` | Те же движки + Setup Engine, композиция сетапа, панель Setup, алерты сетапов, маркеры на ценовой шкале. Будущий webhook (P9) и strategy-сборка (v2.0) идут сюда |

### 4.13 Реестр архитектурных решений (ADR)

| ADR | Решение | Альтернативы | Почему |
|---|---|---|---|
| ADR-01 | Ядро и визуал разделены. Визуал — read-only sink | Модуль = детектор + отрисовка | T-1, v2, тестируемость |
| ADR-02 | Full render на `islastconfirmedhistory`, затем инкрементальный и live-слой | Отрисовка на каждом баре | Производительность. Глобальный ранжир требует видеть все объекты сразу |
| ADR-03 | HTF Feed на подтверждённых барах + общий код движков | Отдельные HTF-детекторы в `request.security` | No-repaint, single source of truth, 1 запрос на HTF |
| ADR-04 | Модульные исходники → монолит при сборке | Публичные библиотеки | IP invite-only, единая версия |
| ADR-05 | Пробой структуры по **закрытию** (по умолчанию), wick — опция | Только wick | Меньше ложных BOS. Соответствует ТЗ §1.3 |
| ADR-06 | Сессии в таймзоне `America/New_York` с DST | UTC | ICT-определения, корректность круглый год |
| ADR-07 | Единая модель `Zone` с `kind` и `state` | Отдельные типы на модуль | Общий lifecycle, общий рендерер, merge |
| ADR-08 | Один агрегированный webhook-`alert()` на бар | `alert()` на каждое событие | Троттлинг платформы, атомарность, порядок |
| ADR-09 | Display Mode задаёт **потолок** видимости. Пользовательский тумблер может только скрыть: `visible = mode.allows(x) AND user.show(x)` | Режим полностью перекрывает тумблеры | Предсказуемо: пользователь всегда может убрать лишнее, режим держит плотность |
| ADR-10 | `varip` запрещён в логике | — | Детерминизм (T-3) |
| ADR-11 | Relevance Score (визуал) и Confluence Score (логика) — разные величины, без перекрёстного использования | Одна общая оценка | T-1: визуал не определяет логику |
| ADR-12 | Внешние ключи событий и объектов строятся от **времени** бара, а не от `bar_index` | bar_index | `bar_index` меняется при сдвиге окна истории. Ключ должен быть стабилен между пересчётами |
| ADR-14 | **Без зависимости от видимой области; отрисовка на закрытии бара** (v0.6): история рисуется по окну последних `histDepth` баров (по сегментам, как раньше), проход отрисовки — на `islastconfirmedhistory` и на каждом закрытом realtime-баре. Всё, что зависело от масштаба (ширина подписей, «щепки» зон, подписи сессий, шаг тегов), оценивается для стандартного зума — `VIEW_BARS` = 200 баров на экране, а не по ширине окна (v0.8.1) | Видимая область (`chart.left/right_visible_bar_time`, v0.2–0.5) и отрисовка на каждом тике | Чтение видимой области заставляло TradingView пересчитывать весь скрипт (≈1,7 с на 10 тыс. баров, в двух индикаторах) при каждой прокрутке и зуме, а отрисовка на `islast` повторялась на каждом тике — «лагает, постоянно перерисовывает». Цена: левее окна истории разметки нет (окно настраивается); AC-M16 (история на всём видимом графике) заменён окном. Проверено пользователем в TradingView: «рисуется не вся история, но хватает» |
| ADR-13 | **Два индикатора из одних исходников** (v0.4.1): SMC Visualizer Pro (`core`) и SMC Pro · Setups (`setups`); код одной цели огорожен `//#if`; бюджет ≤ 34 тыс. токенов на цель (с v0.8.1 — ≤ 30 тыс. токенов кода, строка = 1 токен; та же калибровка); подпись настроек `cfg` в обоих | (1) один монолит — не компилируется (таймаут при ≈40 тыс. токенов); (2) ядро в Pine-библиотеке — публикация раскрывает IP, выигрыш по времени компиляции не проверяем офлайн; (3) урезать функции v0.4 — запас исчезнет с P9 | Компиляция: v0.3.0 ≈30 тыс. токенов ≈ 1 мин, v0.4.0 ≈40 тыс. → таймаут 2 мин; гипотеза «стоимость = число мест вызова» опровергнута (−52% по этой метрике не помогло). Цена решения: движки считаются в двух индикаторах (дольше общая загрузка), настройки движков нужно держать одинаковыми (видно по `cfg`) |

## 5. Архитектура будущей автоматической торговли

### 5.1 Цели и не-цели

**Цели (v2.0+):** превращать сигналы в исполняемые планы с контролем риска; поддерживать бэктест, forward-test и автоматическое исполнение через внешний шлюз; обеспечить безопасность, наблюдаемость и восстановление после сбоев.

**Не-цели:** исполнение ордеров «внутри TradingView» без шлюза (кроме strategy-бэктеста); хранение секретов в Pine; ML-прогноз (v3, внешний).

### 5.2 Целевая схема

```
┌──────────────────────── TradingView (Pine) — «МОЗГ» ────────────────────────┐
│ Core Engines → Setup → Confluence → Signal → Risk → TradePlan               │
│                                                    │                        │
│                                         Execution Adapter                   │
│                         ┌──────────────────────────┴───────────────────┐    │
│                         ▼                                              ▼    │
│        strategy.* (бэктест / forward, сборка strategy)      alert() JSON    │
│                                                       (intent + snapshot)   │
└──────────────────────────────────────────────────────────────────┬──────────┘
                                                                   │ HTTPS webhook
┌──────────────────────── Execution Gateway (внешний) — «ПРЕДОХРАНИТЕЛЬ» ───────┐
│ Receiver (быстрый ACK) → Auth/Allowlist → Schema validation → Idempotency     │
│      → Risk Guard (авторитетный) → Order Manager (bracket/OCO) → Broker API   │
│      → Position Store / Reconciliation → Journal DB → Monitoring/Alerting     │
│      → Notifier (Telegram: подтверждения, semi-auto, kill switch)             │
└───────────────────────────────────────────────────────────────────────────────┘
```

### 5.3 Пути исполнения

| Путь | Описание | Когда |
|---|---|---|
| **A. Strategy-сборка** | То же ядро, Execution Adapter вызывает `strategy.entry/exit`. Бэктест и forward-test в Strategy Tester | v2.0: исследование, калибровка |
| **B. Indicator + webhook** | Indicator шлёт TradePlan-интенты (`PLAN_NEW / PLAN_CANCEL / PLAN_AMEND`), шлюз исполняет | v2.0: основной путь автоматизации (лучший контроль, один источник логики) |
| **C. Strategy + webhook** | Алерты стратегии с `alert_message` на ордерах | Альтернатива B. Минус: TradingView-позиция может разойтись с реальной у брокера |

**Рекомендация:** A — для исследований, B — для исполнения. Pine шлёт **намерения и снимки состояния**, шлюз владеет **реальной позицией**.

### 5.4 Компоненты шлюза (вне Pine, спецификация интерфейса)

| Компонент | Обязанности |
|---|---|
| Receiver | Мгновенный HTTP 200 (TradingView отменяет медленные запросы — по справке порядка 3 с). Обработка асинхронная |
| Auth / Allowlist | Секретный путь URL + allowlist IP-адресов TradingView (список публикует TradingView) + опциональный токен в payload |
| Schema Validator | Проверка `schema`/`v`, обязательных полей. Отказ — в журнал, не в исполнение |
| Idempotency Store | `msg_id` и `plan.id` — повторы игнорируются |
| Risk Guard (авторитетный) | Дневной лимит убытка, макс. позиций и экспозиции, торговые часы, blackout новостей, макс. проскальзывание, **kill switch** |
| Order Manager | Bracket (entry + SL + TP-лестница), OCO, отмена по `expires`, перевод в BE, частичные фиксации |
| Broker Adapter | Маппинг символов TradingView → брокер (CFD/фьючерс/спот), округление цены и лота |
| Reconciliation | Периодическая сверка позиций и ордеров с брокером, восстановление после рестарта |
| Journal DB | Все сообщения, решения Risk Guard, ордера, исполнения — основа trade journal и CSV-экспорта (ТЗ §10 v2.0) |
| Monitoring | Heartbeat-контроль (SNAPSHOT-сообщения), задержки, ошибки, алерты оператору |

### 5.5 Уровни автоматизации (вводятся последовательно)

| Уровень | Название | Что происходит | Критерий перехода |
|---|---|---|---|
| L0 | Visual | Только график | — |
| L1 | Alerts | Алерты и webhook-события, решение принимает человек | Стабильные алерты 4 недели без дублей и пропусков |
| L2 | Shadow | Шлюз принимает планы, «исполняет» виртуально, сравнивает с ручными решениями | ≥ 100 планов, расхождение виртуальных и бэктест-исходов ≤ 5% |
| L3 | Semi-auto | Шлюз готовит ордер, человек подтверждает в Telegram | 4 недели без инцидентов, Risk Guard протестирован |
| L4 | Auto (limited) | Автоисполнение с жёсткими лимитами и kill switch | Решение владельца, лимиты риска согласованы |

### 5.6 Разделение ответственности Pine ↔ Gateway

| Вопрос | Pine | Gateway |
|---|---|---|
| Есть ли сетап, где entry/SL/TP | ✅ авторитетно | читает |
| Размер позиции | расчётный (v2, для информации) | ✅ авторитетно (фактический баланс) |
| Дневной лимит убытка, макс. позиций | индикативно | ✅ авторитетно |
| Факт исполнения, текущая позиция | ❌ не знает | ✅ авторитетно |
| Отмена плана по инвалидации | ✅ шлёт `PLAN_CANCEL` | исполняет; плюс собственный TTL по `expires` |
| Kill switch | — | ✅ |

### 5.7 Обработка сбоев

| Сбой | Защита |
|---|---|
| Пропущенное сообщение | `SNAPSHOT` на каждом закрытом баре (если есть активные планы) → шлюз сверяет и восстанавливает |
| Дубль | `msg_id` + `plan.id` идемпотентны |
| Неупорядоченность | `seq` в батче, `bar_t` монотонно. Устаревшее (`bar_t` < последнего обработанного) — игнор |
| Устаревший сигнал | `expires_t` в плане; шлюз отклоняет план старше `max_signal_age` |
| Алерт остановлен платформой | Heartbeat-таймаут → оповещение оператору, перевод в safe mode (новые входы запрещены) |
| Смена настроек индикатора | `build` и `cfg_hash` в payload. Несовпадение с ожидаемым → блок новых входов до подтверждения |

### 5.8 Безопасность и соответствие

- Никаких ключей брокера в Pine и в сообщениях алертов. Токен в payload — только идентификатор отправителя, авторизация — на стороне шлюза.
- Вебхуки TradingView требуют включённой 2FA и платного тарифа, работают только на портах 80/443.
- Публикация invite-only скрипта с сигналами подчиняется правилам публикации TradingView (никаких обещаний доходности). Описание формулируется как аналитический инструмент.

## 20. Backtesting-ready architecture

### 20.1 Контракт детерминизма

1. Логика — только на подтверждённых барах. Никакого `varip`, никакого `lookahead_on` без смещения `[1]`, никакого `barstate.isrealtime` в логике.
2. Все пороги нормированы (ATR, тики), без зависимости от «текущего времени» (`timenow` запрещён в логике).
3. Порядок движков фиксирован (§4.5). Внутри бара нет обратных зависимостей.
4. Внешние ключи — от времени бара (ADR-12).
5. Warm-up исключает начальный участок из сигналов (§4.8).

### 20.2 Общее ядро для indicator и strategy

Strategy-сборка = те же модули L0–L4 + Execution Adapter со `strategy.*`. Это гарантирует, что бэктест проверяет ровно ту логику, которую трейдер видит на графике.

Рекомендуемые параметры `strategy()`: `calc_on_every_tick = false`, `process_orders_on_close = false` (вход лимитом на следующих барах), комиссия и проскальзывание заданы явно, `use_bar_magnifier = true` при доступности тарифа.

### 20.3 Политика заполнения и внутрибаровой неоднозначности

| Ситуация | Правило (консервативное по умолчанию) |
|---|---|
| Лимит-вход: цена коснулась entry | Исполнено, если `low ≤ entry` (лонг). Опция «требовать проход на N тиков» |
| SL и TP внутри одного бара | **SL первым** (худший случай), если нет bar magnifier |
| Вход и SL в одном баре | Вход, затем SL (худший случай) |
| Гэп через SL | Исполнение по open бара (проскальзывание) |
| Спред (bid-графики FX) | Входной параметр `spread_ticks`, добавляется к SL и входу шорта |

Та же политика используется в Outcome Tracker индикатора: виртуальная статистика и Strategy Tester должны совпадать.

### 20.4 Setup Outcome Tracker (v1.5, в индикаторе)

Для каждого сетапа, достигшего TRIGGERED, виртуально отслеживаются TP1–TP3/SL по политике §20.3. Пишутся `outcome`, `R_realized`, `MFE_R`, `MAE_R`, `bars_to_outcome`. Результаты агрегируются в Analysis-дашборде и, опционально, в журнале событий. Цель — **калибровка скоринга** (связь грейда с исходом), а не реклама доходности.

### 20.5 Метрики

| Группа | Метрики |
|---|---|
| Результат | Win rate, средний R, expectancy (R), profit factor, max drawdown (R), серия убытков |
| Качество сигнала | Распределение исходов по грейдам A+/A/B/C, по моделям, сессиям, HTF-согласованности |
| Исполнимость | Доля MISSED (цена ушла к TP без входа), среднее время до входа, доля EXPIRED |
| Устойчивость | Метрики по инструментам и годам, IS vs OOS |

### 20.6 Протокол исследований

1. Заморозка параметров перед тестом (версия сборки + `cfg_hash`).
2. In-sample / out-of-sample по времени (например, 70/30), затем walk-forward.
3. Минимум 6 инструментов × 3 ТФ. Отчёт — по каждому отдельно, не только в сумме.
4. Ограниченное число настраиваемых весов скоринга (пресеты, §9.6) — защита от переподгонки.
5. **Repaint-аудит:** запись журнала событий в realtime (Bar Replay или реальный рынок) и сравнение с журналом пересчёта истории за тот же отрезок. Совпадение — 100% для классов Confirmed / Delayed / HTF-confirmed.

### 20.7 Экспорт данных

| Канал | Что | Ограничения |
|---|---|---|
| `log.info` (Debug) | CSV-строки событий и исходов в Pine Logs | Ручное копирование. Объём логов ограничен |
| Webhook → коллектор | Поток событий в реальном времени (Journal DB шлюза) | Только realtime, не история |
| Strategy Tester | Список сделок, экспорт из интерфейса TradingView | Только strategy-сборка |
| Служебные plot'ы (`display.data_window`) | Сигнальные серии (dir, entry, sl, tp, grade) для Data Window и внешних скриптов (`input.source`) | Числовые серии, ограниченное количество |

### 20.8 Чек-лист защиты от заглядывания в будущее

- [ ] Нет `lookahead_on` без смещения `[1]`.
- [ ] Пивоты используются только после подтверждения (L баров справа). Время события = бар подтверждения.
- [ ] Метки, поставленные «в прошлом», не участвуют в решениях на барах до подтверждения.
- [ ] Dealing range «developing» не используется для решений как «established».
- [ ] HTF-данные — только закрытые бары.
- [ ] Нет `timenow`, `barstate.isrealtime`, `varip` в логике.
- [ ] Сессионные high/low текущей сессии не считаются «уровнем ликвидности, снятым в будущем».
